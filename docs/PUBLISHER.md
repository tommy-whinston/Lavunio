# Lavunio Publisher → встроенный публикатор

> Статус: ядро встроено в лаунчер. Автор с ролью `author`/`admin` и Lavunio ID создаёт режим и релиз, собирает ZIP с манифестом, загружает сборку и отправляет на модерацию прямо из раздела «Публикация». Отдельный `LavunioPublisher.exe`, статистика и загрузка обложки файлом пока остаются на потом.

## 1. Почему в лаунчер

- Один клиент вместо двух приложений.
- Автору не нужно отдельно устанавливать публикатор.
- Общая авторизация Lavunio.
- Общий UI, тема и обновления.
- Меньше дублирования кода.

## 2. Что должно быть внутри лаунчера

Новый раздел, доступный только авторам:

- «Мои режимы» — черновики, релизы, статусы модерации.
- «Новый режим» — карточка режима.
- «Новый релиз» — версия, changelog, файлы.
- «Загрузка» — прогресс, части файла, ошибки.
- «Статистика» — скачивания, установки, обновления.
- «Настройки автора» — профиль, команда, токены.

## 3. Роли и доступ

- `player` — обычный игрок.
- `author` — видит раздел публикации.
- `moderator` — очередь модерации.
- `admin` — полный доступ.

Роль приходит из API. Публикация без роли `author` невозможна. Локально роль выдают CLI:

```powershell
cargo run --bin role -- author@example.com author
```

## 4. Поток публикации

```text
Черновик режима
  → загрузка обложки
  → создание релиза
  → загрузка сборки
  → проверка файлов (sha256, размер, manifest)
  → submit на модерацию
  → approve / reject
  → релиз появляется в каталоге
```

## 5. API

Используются уже реализованные endpoints:

```text
POST /v1/publisher/modes
GET  /v1/publisher/modes
POST /v1/publisher/modes/{id}/releases
POST /v1/publisher/releases/{id}/assets/upload-url
PUT  /v1/publisher/releases/{release_id}/assets/{asset_id}/upload
POST /v1/publisher/releases/{release_id}/assets/{asset_id}/complete
POST /v1/publisher/releases/{id}/submit
GET  /v1/publisher/modes/{id}/stats
```

`GET /v1/publisher/modes` возвращает режимы автора с релизами и файлами — по нему строится раздел «Публикация».

`upload-url` принимает необязательный `manifest` и сохраняет его у файла сборки. Лаунчер передаёт туда карту файлов, SHA-256 и размеры, поэтому установка идёт по манифесту, без повторного сканирования архива.

`upload-url` возвращает:

```json
{
  "assetId": "...",
  "uploadUrl": "...",
  "method": "PUT",
  "storage": "s3",
  "completeUrl": ".../complete"
}
```

Для S3/R2 встроенный публикатор должен:

1. загрузить файл по `uploadUrl`;
2. вызвать `completeUrl`;
3. только после этого делать `submit`.

Для локального хранилища `completeUrl = null`, файл загружается через API и сразу готов.

Позже:

- multipart upload для больших файлов;
- progress через WebSocket/SSE;
- pre-signed R2/S3 URL;
- автосохранение черновика.

## 6. UI в лаунчере

- В sidebar добавляется пункт «Публикация» для авторов.
- Форма режима переиспользует существующие поля:
  - название, slug, описание, теги, автор, соавторы;
  - обложка, скриншоты;
  - версия, changelog, файлы.
- Статусы:
  - `draft`, `pending`, `published`, `rejected`, `hidden`.
- После submit показывается очередь модерации и причина отклонения.
- Для больших сборок — прогресс и возможность продолжить загрузку.

## 7. Безопасность

- Никаких GitHub-токенов в лаунчере.
- Только токен автора Lavunio с ограниченными scopes.
- Токены хранить в защищённом хранилище ОС, а не в localStorage.
- Проверка ZIP на path traversal и подозрительные файлы на сервере.
- Ограничение размера и rate limit.
- Аудит действий автора.

## 8. Миграция

1. Добавить в лаунчер раздел «Публикация».
2. Подключить создание черновиков и релизов.
3. Подключить загрузку файлов через API.
4. Перенести текущие функции Lavunio Publisher.
5. Оставить отдельный exe на один релиз как fallback.
6. Удалить отдельный exe и GitHub-публикацию.
